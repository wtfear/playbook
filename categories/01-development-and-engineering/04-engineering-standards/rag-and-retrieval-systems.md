# Standard: RAG and Retrieval Systems

> [!NOTE]
> **Candidate Practice / Proposed Scaffolding:** This document contains candidate material for research and evaluation. It does not constitute approved agency policy, mandatory instruction, or contractual commitment until formally reviewed and marked with `status: approved`.

---

## 1. When It Applies

- **Applies to:** Applications, agents, chatbots, and internal search engines that ingest external documents (PDFs, Notion, web pages, databases) and augment model context windows via vector or hybrid search.
- **What Does NOT Apply:** Simple prompt-only LLM completions that rely solely on base model parameters without external knowledge base retrieval.

---

## 2. Must (Mandatory Minimum)

> *Status: [Pending Founder Decision]*
> 
> *The following subtopics represent candidate technical areas to research and evaluate. They do not constitute approved mandatory rules.*

- [ ] **Document Chunking & Metadata Strategy:** Defining semantic chunking strategies (chunk size, token overlap, header hierarchy) and metadata tagging (tenant ID, document date, permission tier, source URI) to maximize retrieval precision.
- [ ] **Embedding Model Versioning:** Pinning embedding models and dimensions; establishing index rebuild procedures when migrating between embedding model versions.
- [ ] **Multi-Tenant Vector Isolation:** Enforcing tenant-level namespace separation or filtered metadata queries in vector databases to prevent cross-tenant data leakage.
- [ ] **Hybrid Search & Reranking:** Evaluating combination strategies (BM25 sparse keyword matching + dense vector similarity) coupled with cross-encoder rerankers (candidate tools: Cohere Rerank, BGE-Reranker) to resolve domain-specific terminology.
- [ ] **RAG Quality Evaluation (The RAG Triad):** Tracking objective retrieval metrics: Context Relevance (signal-to-noise ratio), Groundedness (faithfulness to retrieved chunks), and Answer Relevance (response directly answers user prompt).

---

## 3. Should (Recommended Practice & Judgment)

- What criteria dictate embedding vector search into PostgreSQL via `pgvector` versus provisioning a dedicated managed vector database (e.g., Pinecone, Qdrant, Chroma)?
- How should document updates and deletions be synchronized to the vector index to prevent stale or orphaned knowledge embeddings?
- How should indirect prompt injection embedded inside untrusted retrieved third-party documents be intercepted before reaching model context?

---

## 4. Common Failure Modes

- **Lost-in-the-Middle Context Smothering:** Stuffing 20+ large chunks into context, causing the LLM to ignore crucial instructions placed in the middle of the prompt.
- **Mismatched Embedding Models:** Querying a vector database indexed with Model A using query vectors generated by Model B, returning random noise.
- **Unbounded Document Ingestion:** Parsing raw OCR or uncleaned HTML tables directly into embeddings, filling context with irrelevant formatting tags and noise.

---

## 5. Evidence That It's Done

- [ ] Chunking pipeline unit tests verifying chunk sizes and overlap adhere to configured token budgets.
- [ ] Multi-tenant isolation test proving Tenant A queries never return Tenant B document chunks.
- [ ] Groundedness evaluation harness run on a synthetic test set achieving baseline threshold before deployment.
